# 아키텍처 제안과 기술 선택

## 1. 문서 상태

제품 형태와 애플리케이션 스택은 모바일 우선 반응형 웹앱, TypeScript 기반 React 클라이언트, Node.js/Express API로 확정했다. 약속 데이터의 배포 저장소는 무료 Supabase PostgreSQL로 결정했고 로컬 개발은 SQLite를 유지한다. 웹과 API는 한 Vercel 프로젝트에서 Vite 정적 배포와 Express Function으로 제공한다. 이 문서는 추천 구조와 결정 기준을 제안하며, 스파이크 결과 전의 선택을 확정 사실로 다루지 않는다.

## 2. 설계 목표

- iOS·Android·데스크톱의 주요 브라우저에서 설치 없는 링크 참여 경로를 제공한다.
- 외부 데이터 공급자를 교체해도 추천 규칙을 다시 쓰지 않는다.
- 동일 입력이 동일한 점수·근거를 내도록 추천을 재현 가능하게 만든다.
- 비밀키와 참여자 정밀 위치를 브라우저 번들·클라이언트 로그에 노출하지 않는다.
- 외부 서비스 일부가 실패해도 거짓 정상 상태를 만들지 않는다.
- Codex가 자동 테스트와 반복 검증을 안정적으로 수행할 수 있어야 한다.

## 3. 추천 논리 구조

```text
[모바일 우선 반응형 웹앱]
          |
          v
[약속 API · 권한 · 링크]
          |
          +--------> [약속/참여자 저장소]
          |
          v
[추천 오케스트레이터]
   |      |       |
   v      v       v
[경로] [상황] [공원·만남지점]
 어댑터  어댑터    카탈로그
   \      |       /
    v     v      v
 [정규화된 후보 평가 입력]
          |
          v
[결정 규칙 + 점수 + 설명 근거]
```

구체적인 배포 단위는 초기에는 하나의 백엔드가 될 수 있다. 위 구분은 마이크로서비스 요구가 아니라 코드 경계다.

## 4. 컴포넌트 책임

### 클라이언트

- 방장 약속 생성·자신의 이동 장소 제출, 게스트 이동 장소 제출, 추천 비교, 길찾기 연결
- 서버가 계산한 근거를 표현하되 점수를 별도로 다시 계산하지 않음
- 로딩, 일부 데이터, 오래된 데이터, 실패 상태 표시
- 비밀 API 키와 전체 공유 토큰을 분석 로그에 보내지 않음

### 약속 API

- 방장/게스트 권한과 만료 가능한 공유 링크 처리
- 초대·참가자·방장 권한을 별도 capability token으로 분리하고 토큰 원문은 저장하지 않음
- 입력 검증 및 최소 데이터 보관
- 추천 계산 요청과 결과 버전 연결

### 데이터 어댑터

- 경로, 혼잡, 날씨, 대기, 행사·통제 데이터를 공급자 응답에서 내부 모델로 변환
- 출처, 조회 시각, 대상 시각, 원본 최신성, 오류 상태 유지
- 시간 초과, 재시도, 호출 제한, 캐시 정책을 공급자별로 격리

### 공원·만남 지점 카탈로그

- 한강공원 11곳과 검증된 대표 만남 지점 관리
- 역/출입구와 지점 간 접근 관계, 시설, 좌표, 검증 출처와 변경 이력 보관
- 동적 공공데이터와 수동 검증 데이터를 구분

### 추천 엔진

두 단계로 나눈다.

1. **자격 판정:** 접근 불가, 심각한 통제, 필수 데이터 부재 등 절대 조건으로 후보 제외
2. **순위 계산:** 이동 효율·공평성, 도착 시점 혼잡, 기상, 피크닉 시설, 데이터 신뢰도를 정규화해 비교

엔진의 출력은 총점만이 아니라 요소별 점수, 제외 사유, 비교 문장에 필요한 사실을 포함한다. 가중치는 버전 관리하고 추천 결과에 사용한 버전을 남긴다.

### 설명 생성

규칙 엔진의 구조화된 근거를 템플릿으로 표현한다. 예: 후보 A가 평균 이동시간은 짧지만 행사 통제로 제외되고 후보 B가 선택됐다는 사실을 같은 계산 결과에서 생성한다. 생성형 AI는 MVP 필수 경로에 두지 않는다.

## 5. 데이터 모델 초안

최종 스키마가 아니라 경계를 검증하기 위한 개념 모델이다.

- `Meeting`: 시간, 목적, 일행 이동 패턴, 선택적 방장 지정 공통 출발 장소, 상태, 링크 만료, 정책 버전
- `Participant`: 별칭, 정규화된 출발지 참조, 선택적 약속 후 장소 참조, 이동수단
- `Park`: 공원 식별자, 이름, 지원 상태
- `MeetingPoint`: 좌표, 현장 식별명, 접근 연결, 검증 출처
- `RouteEstimate`: 참여자-지점별 시간, 이동수단, 환승/도보/통행료, 공급자, 계산 시각
- `ConditionSnapshot`: 장소, 관측/예측 대상 시각, 혼잡·날씨·행사·통제, 최신성
- `Recommendation`: 1순위/대안, 규칙 버전, 요소별 점수, 제외 사유, 신뢰 상태
- `RecommendationRevision`: `provisional` 또는 `current` 단계, 이전 결과 참조, 변경 요약, 방장 승인 상태
- `MeetingPoll`: 투표 시작 당시 후보 3곳의 식별자·표시명, 차수, 참여자별 현재 1표, 동률 후보, 투표/랜덤 결정 방식

정확한 출발지 원문과 추천 재현에 필요한 정규화 값의 보관 범위는 개인정보 검토 후 결정한다.

개인정보·공유 링크의 제안 수명주기와 권한 경계는 [`PRIVACY_THREAT_MODEL.md`](./PRIVACY_THREAT_MODEL.md)에 기록한다. 사용자 승인 전에는 제안값을 운영 정책으로 간주하지 않는다.

## 6. 확정 기술 스택과 코드 구조

### 제품 형태 — 확정

- 모바일 우선 반응형 웹앱 하나를 제공한다.
- 방장과 참여자가 같은 웹 제품을 역할에 따라 사용한다.
- 공유 URL을 핵심 진입점으로 삼고, 네이티브 앱 설치를 요구하지 않는다.
- 방장 화면은 공식 카카오 JavaScript SDK의 카카오톡 공유를 우선 사용한다. 공개 JavaScript 키만 클라이언트에 주입하고 등록 웹 도메인으로 제한하며, 서버용 REST 키는 번들에 포함하지 않는다. SDK를 사용할 수 없는 환경에는 Web Share와 링크 복사를 대안으로 둔다.
- Android·iOS 네이티브 앱은 MVP에서 만들지 않는다.
- PWA 설치 기능은 웹앱 사용성에 실제 이점이 확인될 때만 추가하며, 서비스 이용의 전제조건으로 삼지 않는다.

### 확정 애플리케이션 스택

- **클라이언트:** TypeScript + React
- **API:** TypeScript + Node.js + Express
- **계약:** 클라이언트와 API가 공유하는 런타임 스키마 및 타입
- **추천 도메인:** Express 라우트와 분리된 순수 TypeScript 모듈

단일 저장소 안에 최상위 `frontend`와 `backend` 경계를 둔다. 백엔드 내부는 domain, application, infrastructure, presentation 계층으로 의존성 방향을 고정한다. Vercel 배포 진입점 `api/server.ts`는 동일한 live composition을 불러오는 얇은 어댑터이고, 브라우저와 API는 같은 HTTPS origin을 사용한다.

저장소는 application의 비동기 repository port 뒤에 둔다. `DATABASE_URL`이 설정된 배포 서버는 Supabase PostgreSQL을 사용하고, 로컬 기본값은 Node 22.13 이상에서 제공되는 내장 SQLite와 루트 `.data/meetings.sqlite`다. 테스트는 격리를 위해 메모리 저장소 또는 임시 SQLite를 주입한다. 두 구현 모두 같은 만료 규칙과 capability 해시 색인을 사용하며 토큰 원문·정밀 좌표·집 주소는 저장하지 않는다. PostgreSQL 스키마는 `backend/migrations`에 기록하고 서버 시작 시 누락 테이블과 인덱스를 멱등 생성한다.

프론트엔드는 Supabase Data API에 직접 접근하지 않는다. Express API만 서버 전용 `DATABASE_URL`로 연결하므로 Supabase Auth·Realtime·Storage와 공개 service-role 키는 현재 범위에 포함하지 않는다. IPv4 장기 실행 서버는 Session pooler, 서버리스는 Transaction pooler를 사용한다. 무료 프로젝트의 저활동 일시 정지와 자동 백업 부재를 MVP 제한으로 기록하고, 유료 전환은 자동으로 수행하지 않는다.

같은 브라우저는 `localStorage`에 최근 약속의 ID와 시각만 최대 5개 저장하고 HttpOnly 방장 쿠키로 실제 권한을 검증한다. 다른 기기 복구 링크는 256비트 방장·초대 capability를 URL fragment에 담는다. 복구 화면이 fragment를 읽어 서버에서 해시를 검증하고 쿠키를 발급한 뒤 즉시 URL을 정리한다. 방장 화면은 필요할 때만 새 복구 링크를 만들며 활성 capability 수를 제한한다.

게스트가 장소 제출을 완료하면 해당 초대 API 경로로 제한된 HttpOnly 참여자 capability 쿠키를 발급한다. 서버에는 해시만 참여자와 연결해 저장한다. 참여자 세션 API는 이 capability로 제출 여부와 현재 추천 상태만 복원하고 장소 원문은 반환하지 않는다. 같은 capability의 재제출은 기존 상태를 반환해 중복 참여를 만들지 않는다. 투표 API는 이 capability 또는 방장 capability로 1인 1표를 판정한다. 투표는 추천 엔진 입력이나 순위를 변경하지 않고, 시작 당시 추천 1곳·대안 2곳을 스냅샷으로 저장하는 별도 약속 상태다. 랜덤 동률 해소는 application port 뒤의 암호학적 난수 구현을 사용해 테스트에서 결정적으로 대체할 수 있게 한다.

### 경계 원칙

- React는 입력·상태 표시와 접근성을 담당하고 추천 점수를 다시 계산하지 않는다.
- Express는 권한, 입력 검증, 외부 API 오케스트레이션과 추천 실행을 담당한다.
- 공유 스키마는 API 요청·응답을 검증하며 TypeScript 타입만으로 런타임 입력을 신뢰하지 않는다.
- 추천 엔진은 HTTP, React, DB, 공급자 SDK에 의존하지 않는 순수 도메인 코드로 유지한다.
- 이동 패턴은 도메인 입력에 방향별 경로를 분리해 전달하며 방장도 `Participant`로 추천 계산에 포함한다. 함께 출발 패턴은 참여자의 출발 입력을 받지 않고 약속의 방장 지정 공통 출발 장소를 사용한다. 공급자 어댑터는 `출발 장소 → 공원`과 `공원 → 귀가 장소`의 방향을 보존하고 공통 출발 경로를 중복 호출하지 않는다.
- `Participant.travelMode`는 `public_transit | car`이며 기존 저장 데이터는 대중교통으로 해석한다. 대중교통 어댑터는 장소↔집결점을 직접 조회하고, 자가용 어댑터 조합은 장소↔공원별 기준 주차장의 운전 경로와 주차장↔동일 공통 집결점의 도보 경로를 더한다. 도메인 추천 엔진에는 최종 분 단위 경로만 전달해 두 수단에 동일한 공평성 규칙을 적용한다.
- 외부 API 비밀키와 정밀 위치는 브라우저 번들·클라이언트 로그에 두지 않는다.
- 저장하지 않기로 한 주소 원문·정밀 좌표는 요청 처리 경계에서 폐기하고 테스트로 증명한다.

### 확정된 애플리케이션 하네스

- npm workspaces로 `frontend`와 `backend`를 관리한다.
- Vite로 React 웹 개발 서버와 프로덕션 빌드를 실행한다.
- Express API는 `tsx`로 개발 실행하고 TypeScript로 빌드한다.
- 추천 규칙은 Express·저장소·외부 공급자를 모르는 `backend/src/domain`의 순수 TypeScript에 둔다.
- application use case는 repository·token·추천 데이터 port에만 의존하고 infrastructure가 이를 구현한다.
- Express 요청·쿠키·응답 변환은 `backend/src/presentation`에 제한한다.
- React는 `app`, `pages`, `features`, `shared` 경계로 나누고 공통 API 계약과 HTTP 처리를 화면에서 분리한다.
- 루트 `npm run check`에서 strict 타입 검사, 테스트, 전체 빌드를 수행한다.
- 하네스 선택은 [`ADR 001`](./adr/001-application-harness.md), 계층과 의존성 방향은 [`ADR 002`](./adr/002-clean-architecture-boundaries.md)에 기록한다.

### 아직 선택하지 않는 항목

- React 라우터
- 웹·API 배포 서비스
- 인증 또는 방장 식별 구현체
- PWA 적용 여부

이 선택은 데이터 스파이크와 얇은 프로토타입에 필요한 최소 범위에서, 의존성 상태·라이선스·자동 검증·배포 비용을 비교한 뒤 결정한다.

프로토타입에서 다음을 검증한다.

- 공유 링크의 모바일 브라우저 진입과 링크 미리보기
- 날짜·출발지 입력의 접근성과 키보드 사용성
- iOS Safari, Android Chrome, 데스크톱 브라우저 호환성
- 지도 앱/지도 웹 연결과 폴백
- 새로고침·뒤로가기·링크 재진입 시 상태 일관성
- 단위·컴포넌트·E2E 테스트의 CI 실행시간과 안정성
- 저사양 모바일 기기의 초기 로딩과 전송 크기

## 7. 백엔드 인프라 선택 원칙

API 런타임은 Vercel Node.js Function의 Express, 배포 데이터베이스는 Supabase PostgreSQL로 확정했다. 별도 ORM 없이 `pg` 어댑터를 repository port 뒤에 두고 서버리스용 Transaction pooler를 사용한다. Vercel 환경에서 `DATABASE_URL`이 없으면 임시 파일 DB로 대체하지 않고 기동에 실패한다.

필수 조건:

- 비밀키가 서버 측에만 존재
- 만료 가능한 초대 토큰과 행 단위 권한 구현 가능
- 위치 데이터 삭제와 보관 기간 제어 가능
- 외부 API 호출 제한, 캐시, 작업 큐 또는 예약 갱신 지원
- 로컬/CI에서 공급자 fake로 통합 테스트 가능
- 공급자 종속 기능을 도메인 계층과 분리

관리형 BaaS는 빠른 시작과 인증/DB 통합이 장점이지만, 공개 클라이언트 정책과 행 권한 설정 오류가 위험하다. 전용 API 서버는 경계를 명확히 하기 쉽지만 운영 부담이 늘어난다. 데이터 스파이크의 호출 형태와 갱신 작업 요구를 본 뒤 선택한다.

## 8. 캐시·회복 전략

- 공원/만남 지점 같은 정적 데이터와 혼잡/날씨 같은 시계열 데이터의 캐시 정책을 분리한다.
- 데이터마다 허용 최신성(`fresh`, `stale`, `unavailable`)을 정의한다.
- 재시도는 횟수 제한과 지수형 지연을 적용하고 호출 제한 응답을 존중한다.
- 부분 실패 시 추천 가능 여부를 필수 데이터 행렬로 판정한다.
- 이전 결과를 사용할 경우 조회 시각을 명시하고 현재 값으로 위장하지 않는다.
- 외부 공급자 장애를 관찰할 수 있는 구조화 로그와 최소 상태 지표를 둔다.

### 2단계 추천 상태

- `provisional`: 혼잡 예측 범위 밖에서 계산한 임시 추천
- `current`: 예측 범위 안에서 도착 시각 혼잡을 포함해 계산한 최신 추천

서버는 예측 반영이 시작되는 `meetingAt - 12시간`을 결과의 `refreshAt`으로 제공한다. 열린 방장·참여자 화면은 이 시점에 결과를 다시 조회한다. 초대 링크용 갱신 응답은 공원별 집계만 제공하고 참여자 별칭·개인별 이동시간은 제거한다.
- 추천 결과는 덮어쓰지 않고 규칙·데이터 버전과 함께 개정본으로 저장한다.
- 갱신 작업은 멱등하게 설계하고 같은 입력·데이터 버전으로 중복 알림을 만들지 않는다.
- 최신 추천이 확정 장소와 다르면 `pending_host_approval` 상태로 두며, 승인 전 공유된 확정 장소를 변경하지 않는다.
- 예약 실행 수단은 배포 환경 선택 후 결정하고, 실패 시 방장이 직접 갱신할 수 있는 폴백을 제공한다.

## 9. 테스트 전략

- **도메인 단위 테스트:** 자격 판정, 정규화, 가중치, 공평성, 동률, 설명 근거
- **계약 테스트:** 저장된 익명 응답 fixture로 공급자 변환 검증
- **통합 테스트:** fake 어댑터와 실제 DB 경계를 이용한 추천 생성
- **장애 테스트:** 시간 초과, 429, 오래된 값, 일부 참여자 경로 누락
- **컴포넌트 테스트:** 핵심 화면의 모든 상태와 접근성
- **E2E 테스트:** 방장 생성 → 게스트 참여 → 추천 → 지도 연결
- **소수 실데이터 점검:** 약관과 비용 한도 안에서 정기적으로 계약 변화 감지

실제 API를 모든 CI 테스트에서 호출하지 않는다.
