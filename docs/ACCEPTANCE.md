# MVP 시나리오 기반 인수 기준

이 문서는 사용자가 코드를 읽지 않고 제품 결과를 검수하기 위한 기준이다. 각 시나리오는 배포 후보에서 반복 실행할 수 있어야 하며, 가능한 항목은 자동화 테스트로도 고정한다.

## 공통 판정 원칙

- 핵심 여정을 막는 오류가 하나라도 있으면 MVP는 불합격이다.
- 외부 데이터가 일부 없어도 서비스가 근거 없이 정상처럼 보이면 불합격이다.
- 추천 결과와 표시된 이유가 동일한 입력으로 재현되지 않으면 불합격이다.
- 시간 목표와 허용 오차는 데이터 스파이크에서 기준선을 측정한 뒤 별도 확정한다.

## A. 약속 생성과 게스트 참여

### A1. 방장이 피크닉 약속을 만든다

**준비:** 신규 사용자 상태로 서비스를 연다.

**행동:** 날짜와 시간만 정해 약속을 생성한다.

**통과 기준:**

- 피크닉 목적이 명확히 표시된다.
- 필수 입력과 선택 입력이 구분된다.
- 과거 시간이나 해석 불가능한 입력은 구체적인 수정 안내와 함께 차단된다.
- 모바일에서 브라우저 기본 날짜 입력 대신 앱 색상과 터치 영역을 적용한 바텀시트가 열리고, 선택 중인 날짜·시·분과 확정 결과를 명확히 확인할 수 있다.
- 회원가입을 요구하지 않고 공유 가능한 약속이 생성된다.
- `함께 출발 · 각자 귀가`와 `각자 출발 · 각자 귀가`의 차이를 확인하고 하나를 선택할 수 있다.
- 함께 출발에서는 방장이 공통 출발지와 자신의 귀가 장소를 입력한다. 각자 출발에서는 자신의 출발 장소와, 필요할 때 다른 약속 후 장소를 입력하며 추천 인원에 포함된다.
- 함께 출발 패턴에서는 방장이 공통 출발 장소를 저장하기 전까지 초대 링크 공유를 진행할 수 없다.
- 방장이 자신의 이동 장소를 저장하기 전까지 초대 링크 공유를 진행할 수 없고, 저장 후에는 방장 1명이 참여 완료로 표시된다.
- 최소 2명부터 추천을 시작하며 최대 8명까지 참여할 수 있다는 정원이 `1/2`처럼 최대 2명으로 오해되지 않게 표시된다.
- 카카오 JavaScript 키와 배포 도메인이 설정된 환경에서는 카카오톡 공유 화면을 직접 열고, 사용할 수 없는 환경에는 링크 복사를 제공한다.

### A2. 친구가 브라우저에서 바로 참여한다

**준비:** 다른 기기 또는 비로그인 브라우저에서 공유 링크를 연다.

**행동:** 이름 또는 별칭과 출발역/공개 장소를 입력한다.

**통과 기준:**

- 앱 설치와 계정 생성 없이 모바일 브라우저에서 제출할 수 있다.
- 출발지 후보를 구분할 수 있고 잘못된 위치를 수정할 수 있다.
- 장소 필드를 누르면 검색 입력창과 결과가 같은 전체 높이 바텀시트에 표시되며, 장소 선택·재검색·취소를 키보드 흐름을 끊지 않고 수행할 수 있다.
- 대중교통·자가용 중 실제 이용할 수단을 선택하고, 자가용은 주차 후 공통 집결점까지의 도보를 포함한다는 안내를 확인할 수 있다.
- 현재 위치나 정확한 주소 입력을 요구하거나 제공하지 않는다.
- 수집 목적과 보관/삭제 안내를 제출 전에 확인할 수 있다.
- 제출 후 본인의 입력 내용을 확인할 수 있다.
- 다른 참여자의 정확한 출발 위치는 권한 없이 노출되지 않는다.
- 함께 출발 패턴에서는 방장이 정한 공통 출발 장소를 확인하고 자신의 약속 후 공개 장소만 선택한다.
- 각자 출발 패턴에서는 가까운 출발 공개 장소를 선택하면 `출발 장소로 돌아가요`가 기본 적용되어 두 번째 검색을 요구하지 않는다. 이를 해제한 참여자에게만 약속 후 이동할 공개 장소 검색을 추가로 보여준다.
- 약속 후 장소도 정확한 집 주소 입력을 요구하거나 제공하지 않고 다른 참여자와 방장에게 노출하지 않는다.

### A3. 손상되거나 만료된 링크를 연다

**통과 기준:** 빈 화면이나 일반 오류 대신 링크 상태와 다음 행동을 안내한다. 임의의 약속에 연결되지 않는다.

## B. 추천 결과

### B1. 이동시간만으로 가장 가까운 곳이 정답이 아닌 사례

**준비:** 가까운 후보는 도착 시점 행사 혼잡이 높고, 다음 후보는 각 참여자의 이동이 조금 늘지만 혼잡과 시설 조건이 나은 고정 fixture를 사용한다.

**행동:** 추천을 계산한다.

**통과 기준:**

- 추천 1곳과 역할이 다른 대안 2곳이 명확히 구분된다.
- “가까운 후보보다 얼마나 더 이동하지만 무엇이 나아 추천했는지”가 실제 계산값으로 설명된다.
- 참여자별 이동시간, 평균, 최장 시간 또는 편차를 확인할 수 있다.
- 탈락한 가까운 후보의 핵심 비추천 이유를 확인할 수 있다.
- 세 후보마다 도착 시점 혼잡 상태, 대표 즐길거리, 장점과 계절·예약 등 이용 제한을 확인할 수 있다.
- 공원 특징은 출처가 연결되고 확인되지 않은 시설을 생성하지 않는다.
- 공원을 확정하면 추천 결과보다 먼저 확정 공원의 만남 장소, 공식 즐길거리 3개와 주의사항이 나타난다.
- 방장과 장소를 제출한 참여자는 같은 확정 상태를 확인하고 주변 맛집·카페·편의점을 추가 서버 API 호출 없이 카카오맵 최신 검색으로 열 수 있다.

### B2. 한 참여자에게 지나치게 불공평한 사례

**준비:** 평균은 비슷하지만 한 명의 이동시간이 매우 긴 후보와, 최장 이동시간이 낮은 후보를 비교한다.

**통과 기준:** 공평성 규칙이 결과에 반영되고, 어느 참여자의 정확한 주소도 결과 설명에 노출되지 않는다.

### B3. 절대 제외 조건이 있는 사례

**준비:** 통제, 심각한 기상 위험 또는 접근 불가로 사용할 수 없는 후보를 포함한다.

**통과 기준:** 해당 후보는 단순 감점이 아니라 정의된 규칙에 따라 제외되며, 제외 사유와 데이터 기준 시각이 표시된다.

### B4. 비슷한 점수의 후보

**통과 기준:** 동률 처리 규칙이 항상 동일하게 적용된다. 근소한 차이를 압도적 우위처럼 표현하지 않는다.

### B5. 대안이 단순 점수 순위표가 아닌 사례

**준비:** 상위 후보 여러 곳의 이동 점수는 비슷하지만 대표 즐길거리 구성이 다른 fixture를 사용한다.

**통과 기준:** 첫 대안은 이동 균형이 다음으로 좋은 후보이고, 두 번째 대안은 상위권에서 추천·첫 대안과 다른 대표 경험을 가진 후보다. 세 후보는 중복되지 않고 각 후보를 선택할 이유가 표시된다.

### B6. 방장이 후보 중 장소를 확정한다

**행동:** 추천 또는 대안의 장소 확정 버튼을 누른다.

**통과 기준:** 방장 권한으로만 세 후보 중 하나를 확정할 수 있고 새로고침 뒤에도 확정 상태가 유지된다. 초대 링크만으로는 확정할 수 없다.

### B7. 귀가 경로가 추천을 바꾸는 사례

**준비:** 갈 때만 보면 A 공원이 낫지만, 귀가까지 보면 B 공원이 귀가 최장시간을 크게 줄이는 고정 fixture를 사용한다.

**통과 기준:** 갈 때와 약속 후를 각각 평균·최장·차이로 평가하고 두 방향을 50%씩 반영한다. 방향별 실제 차이에서 “갈 때 평균은 더 걸리지만 귀가 최장시간을 줄인다”는 설명을 만들며 한 방향이라도 경로가 누락된 후보는 제외한다.

결과 화면은 약속이 공식 혼잡 예측 범위 안이면 `이동시간 + 도착 혼잡 반영`, 범위 밖이면 `이동시간 기준 임시 추천`이라고 구분하고 혼잡 갱신 시점을 안내한다.

추천 결과는 추천 공원과 갈 때·귀가 평균, 친구 간 편차, 해당 공원의 혼잡 상태를 먼저 보여준다. 그 아래에는 대안 2곳을 압축해 비교하고, 같은 조회에서 얻은 11개 한강공원의 혼잡 단계를 그래프로 표시한다. 예측 범위 안에서는 약속 시각 예상 혼잡을 추천에 반영하고, 범위 밖에서는 현재 관측임과 추천 미반영 상태를 구분한다. 그래프를 위해 서울시 API를 중복 호출하지 않는다.

### B8. 함께 출발 경로를 재사용하는 사례

**준비:** 방장이 공통 공개 출발 장소를 입력하고 두 참여자가 서로 다른 귀가 장소를 제출한다.

**통과 기준:** 공통 출발 장소에서 11개 공원까지의 경로는 한 번씩만 호출하고 참여자별로 재사용한다. 공원에서 서로 다른 귀가 장소로 가는 경로는 방향을 보존해 따로 계산한다. 참여가 시작된 뒤 공통 출발 장소 변경은 차단된다.

### B8-1. 다른 약속과 서버 재시작에서도 경로를 재사용한다

**준비:** 같은 공급자·출발 장소·도착 장소 조합을 두 개의 서로 다른 약속에서 2시간 안에 계산하고 중간에 서버 저장소 인스턴스를 다시 연다.

**통과 기준:** 외부 경로 API는 한 번만 호출되고 두 번째 약속은 같은 정규화 결과를 사용한다. 저장 키에는 장소명·좌표가 없고 장소 ID 조합의 해시만 남는다. 공급자별 일일 요청 수는 재시작 뒤에도 유지되며, 실제 한도 초과 응답 뒤에는 다른 경로에 대한 추가 호출도 중단된다.

### B9. 추천 후보로 친구 투표를 연다

**준비:** 추천 1곳과 역할이 다른 대안 2곳이 계산되고 방장이 아직 장소를 확정하지 않았다.

**통과 기준:**

- 투표는 기본 확정 흐름을 방해하지 않는 보조 행동으로 제공되며 현재 세 후보만 사용한다.
- 방장과 장소를 제출한 참여자만 1인 1표를 행사하고 마감 전에는 표를 바꿀 수 있다. 초대 링크만 가진 사람의 투표와 중복 투표는 거부한다.
- 전원이 투표하면 자동으로 집계하고, 전원 투표 전에는 방장이 현재 참여 인원을 확인한 뒤 명시적으로 마감할 수 있다.
- 참여자 주 capability 원문은 HttpOnly 쿠키로만 전달되고 DB·응답 본문·로그에 남지 않는다. 카카오톡·외부 브라우저 재진입용 별도 복구 키는 장소 제출 직후 응답으로 한 번 전달해 같은 출처 브라우저 저장소에 약속별로 최대 7일 보관하고, 서버에는 해시만 저장한다. 이 키는 해당 참여 상태 복원과 투표 외의 권한을 갖지 않는다.
- 방장은 기존 초대 권한을 유지한 투표 보기 URL을 카카오톡 메시지로 공유하고 투표 인원과 후보별 득표를 확인할 수 있다. 메시지의 `투표하러 가기`는 후보와 투표 상태로 바로 진입하며, 장소를 제출하지 않은 사람에게는 입력으로 돌아가는 행동을 제공한다.
- 단독 1위는 투표 결과로 표시하되 방장이 다시 확정해야 확정 장소가 된다.
- 동률 마감 시 동률 후보만 남긴 재투표 또는 명시적인 랜덤 선택을 제공한다. 랜덤은 자동 실행하지 않고 결과에 결정 방식을 표시한다.
- 랜덤 선택은 서버가 결과를 먼저 저장한 뒤 약 1.5초 동안 동률 후보를 섞는 연출과 결과 공개를 보여준다. 운영체제에서 모션 감소를 요청한 사용자는 연출을 건너뛴다.
- 투표 시작 뒤 추천이 갱신돼도 이미 열린 투표 후보와 이름은 시작 당시 스냅샷으로 유지한다.

## C. 정확한 만남 장소와 길찾기

### C1. 공원 내부 만남 지점을 확인한다

**통과 기준:**

- 공원 이름만이 아니라 역 출구, 출입구, 안내센터 등 현장에서 식별 가능한 지점이 제공된다.
- 명칭, 좌표, 접근 기준이 검증된 데이터와 일치한다.
- 왜 그 지점이 선택됐는지(대중교통 접근 등)를 확인할 수 있다.

### C2. 지도 서비스로 이동한다

**통과 기준:** 모바일에서는 설치된 지도 앱 또는 지도 웹의 정확한 목적지로 열리고, 데스크톱이나 미지원 환경에는 지도 웹 또는 복사 가능한 장소명/주소 등 대체 행동이 제공된다.

## D. 도착 시점의 상황

### D1. 12시간보다 먼 약속을 만든다

**통과 기준:**

- 결과가 임시 추천임을 결론 근처에서 확인할 수 있다.
- 생성 직후 한 번만 뜨는 안내에서 현재는 이동 기준 1차 추천이며, 약속 12시간 전 방장 페이지를 다시 열면 도착 혼잡으로 재계산한다는 사실을 확인할 수 있다. 새로고침에는 안내가 반복되지 않는다.
- 11개 공원의 현재 혼잡 그래프에는 이동 기준 추천 배지가 붙지 않으며 `오늘 지금 기준` 참고 정보임을 확인할 수 있다.
- 혼잡은 예측 범위 밖 또는 반영 대기로 표시하고 임의의 혼잡 단계를 보여주지 않는다.
- 언제 최신 추천을 계산할지 안내한다.
- 혼잡을 제외하고 사용한 근거와 데이터 누락을 구분해 표시한다.

### D2. 약속이 12시간 이내로 들어온다

**통과 기준:** 결과 화면을 열어 둔 경우 12시간 경계에서 최신 추천이 자동으로 계산되고, 다시 방문하거나 방장 새로고침을 해도 즉시 최신 결과를 받는다. 현재 관측과 도착 시점 예측이 혼동되지 않으며, 각각의 기준 시각·갱신 시각·출처가 표시된다. 추천이 유지됐는지 바뀌었는지 화면에서 확인할 수 있다.

### D3. 최신 추천이 기존 확정 장소와 다르다

**통과 기준:** 새 후보, 기존 장소와의 차이, 변경 이유를 방장이 확인할 수 있다. 방장 승인 전에는 확정 장소와 참여자 안내가 자동으로 바뀌지 않는다.

### D4. 비 또는 강풍이 예상된다

**통과 기준:** 피크닉 적합도에 미치는 영향이 추천에 반영되고 근거가 표시된다. 예보를 확정 사실로 표현하지 않는다.

### D5. 혼합 이동수단을 같은 공평성 규칙으로 비교한다

**준비:** 한 참여자는 대중교통, 다른 참여자는 자가용을 선택한다.

**통과 기준:** 대중교통은 장소↔공통 집결점 경로, 자가용은 장소↔기준 주차장 운전과 주차장↔공통 집결점 도보를 합산한다. 임의 배율 없이 실제 분을 동일한 평균 40%·최장 40%·차이 20% 규칙에 넣는다. 운전 또는 도보 경로가 하나라도 없으면 후보를 제외하고, 화면에 수단별 인원과 참여자별 수단 및 주차 대기시간 미포함을 표시한다.

## E. 데이터 장애와 신뢰

### E1. 혼잡도 데이터만 누락된다

**통과 기준:**

- 나머지 데이터로 결과를 제공할 수 있는지 정의된 정책에 따라 처리한다.
- 누락된 정보와 추천 신뢰도 저하가 눈에 띄게 표시된다.
- 혼잡도를 정상 또는 낮음으로 간주하지 않는다.

### E2. 경로 API가 실패하거나 제한에 걸린다

**통과 기준:** 잘못된 이동시간으로 추천하지 않고 재시도 또는 나중에 확인 안내를 제공한다. 공급자 일일 한도 초과는 일반 경로 누락과 구분해 표시한다. 성공한 동일 참여자 구성·추천 단계는 PostgreSQL/SQLite 결과를 재사용하며, 새로고침·재접속·투표·확정과 동시 조회가 외부 경로를 중복 호출하지 않는다. 참여자 추가 또는 약속 12시간 전 단계 변경만 새 계산을 허용한다.

### E3. 오래된 데이터가 반환된다

**통과 기준:** 최신성 기준을 넘긴 데이터는 현재 데이터처럼 사용하지 않는다. 표시, 감점 또는 추천 중단 중 사전에 정의한 정책이 적용된다.

### E4. 일부 참여자 또는 한 방향의 경로만 계산되지 않는다

**통과 기준:** 계산된 사람이나 계산된 방향만으로 “모두에게 공평한” 추천을 확정하지 않는다. 누락 참여자·방향과 필요한 수정 행동을 알려준다.

## F. 변경과 개인정보

### F1. 참여자가 출발지를 수정한다

**통과 기준:** 추천이 새 입력으로 다시 계산되고 이전 결과와 섞이지 않는다. 변경 사실을 방장이 식별할 수 있다.

### F2. 방장이 약속을 삭제한다

**통과 기준:** 방장 화면의 약속 관리 영역에서 취소를 선택하면 참여 정보와 초대 링크가 함께 삭제된다는 확인 바텀시트를 먼저 보여준다. 방장이 명시적으로 다시 확인한 뒤 약속과 연결된 위치 데이터가 즉시 삭제되고 기존 초대·방장 링크로 접근할 수 없으며, 같은 기기의 `진행 중인 약속`에서도 제거된다. 초대 링크 권한만으로는 취소할 수 없다.

### F3. 입력값과 로그를 점검한다

**통과 기준:** UI, DB, 분석 이벤트, 오류 로그, 테스트 fixture에 비밀키·출발 또는 약속 후 장소의 집 주소 원문·정밀 좌표·실제 공유 토큰이 불필요하게 남지 않는다. 원문을 즉시 폐기하도록 정한 경우 저장소와 로그에 남지 않았다는 검증 증거가 있다.

### F4. 권한과 자동 삭제를 확인한다

**통과 기준:**

- 초대 링크만으로 방장 기능이나 기존 참가자 수정 기능을 사용할 수 없다.
- 방장과 다른 참가자는 참여자의 출발지를 볼 수 없다.
- 참가자는 자신의 출발지만 확인·수정·삭제할 수 있다.
- 미완성 약속은 생성 7일 후, 확정 약속은 약속 시각 24시간 후 접근할 수 없고 연결 데이터가 삭제된다.
- 방장 수동 삭제는 즉시 링크를 무효화하며 다른 약속으로 연결하지 않는다.
- 같은 브라우저의 홈에서는 위치 정보 없이 약속 ID와 시간만 저장한 `진행 중인 약속`으로 돌아갈 수 있다.
- 다른 브라우저에서는 방장이 별도로 보관한 방장 전용 링크로 쿠키를 복구할 수 있다. 링크 원문은 서버·로그·DB에 저장되지 않고 복구 직후 주소에서 제거된다.
- 장소를 제출하지 않은 브라우저가 초대 링크를 열면 장소 입력을 기본 행동으로 보여준다. 반면 유효한 참여자 capability 쿠키 또는 약속별 복구 키가 있는 브라우저는 새로고침·카카오톡 재진입 시 입력폼을 다시 보여주지 않고 추천 결과 또는 제출 완료 대기 상태를 복원한다. 복구 키가 유효하면 서버는 HttpOnly 참여자 쿠키를 다시 발급한다. 같은 capability나 복구 키로 참여 제출 API를 다시 호출해도 인원이 중복 증가하지 않으며, 복원 응답에는 장소 원문을 포함하지 않는다.
- 계정·이메일·전화번호를 통한 복구 기능이 있는 것처럼 안내하지 않는다.

## G. MVP 최종 검수 묶음

출시 후보는 다음 증거를 한곳에서 제공해야 한다.

- A1 → A2 → B1 → C1 → C2로 이어지는 모바일 브라우저 핵심 여정
- B2~B4 추천 규칙 자동 테스트 결과
- E1~E4 장애 주입 결과
- 접근성 기본 점검(텍스트 확대, 스크린리더 레이블, 색상 외 상태 표현, 터치 영역)
- iOS Safari, Android Chrome, 데스크톱 브라우저의 지원 범위와 실제 검증 결과
- 사용한 외부 데이터의 출처, 약관, 호출 한도, 갱신주기 확인표
- 알려진 제한과 미완료 항목
