# 추천 규칙 실험안

규칙 버전: `spike-v1`

상태: **균형 중심 방향 승인 — 정확한 가중치와 운영 규칙은 실험 중**

작성일: 2026-08-12

## 목표

같은 정규화 입력은 항상 같은 추천·대안·근거를 만든다. 생성형 AI는 결정에 참여하지 않으며, 설명은 계산에 사용한 값과 상태에서만 만든다.

## 처리 순서

1. 참여자별 경로가 모두 있는지 확인한다.
2. 폐쇄·위험 기상·필수 화장실 누락 후보를 제외한다.
3. 평균 이동시간, 최장 이동시간, 최대-최소 범위를 계산한다.
4. 추천 단계에 맞는 최신 혼잡·날씨·행사·통제만 반영한다.
5. 정책별 이동 부담과 상황·신뢰 부담을 합산해 오름차순으로 정렬한다.
6. 전체 1순위, 이동 균형 차순위, 상위권의 다른 즐길거리 대안을 반환하고 같은 계산값과 출처 있는 공원 카탈로그로 근거를 만든다.

## 세 후보 출력 규칙

- **오늘의 추천:** 전체 부담 정렬 1순위다.
- **이동 균형 대안:** 동일한 정렬의 2순위다.
- **다른 즐길거리 대안:** 상위 7개 안에서 앞의 두 후보에 없는 대표 경험 태그를 가진 첫 후보다. 없으면 안정적인 3순위를 사용한다.
- 세 후보는 중복되지 않는다.
- 공원 즐길거리는 1순위 점수에 임의의 가산점을 주지 않으며, 선택지를 이해하는 정적 근거로 먼저 검증한다.
- 특징과 이용 제한은 [`PARK_EXPERIENCES.md`](./PARK_EXPERIENCES.md)의 공식 출처 기반 카탈로그에서만 가져온다.

## 공평성 비교 정책

현재 세 정책은 결과 차이를 보기 위한 실험용이다.

| 정책 | 평균 | 최장 | 범위 | 의도 |
|---|---:|---:|---:|---|
| `average-only-spike-v1` | 100% | 0% | 0% | 일행 전체 이동량 우선 |
| `balanced-spike-v1` | 40% | 40% | 20% | 전체 효율과 한 사람의 과도한 부담을 함께 제한 |
| `minimax-spike-v1` | 0% | 100% | 0% | 가장 오래 이동하는 사람 우선 |

가중합 값은 내부 비교용이며 사용자에게 객관적인 품질 점수처럼 표시하지 않는다. 평균·최장·범위가 서로 연관된 값이므로 `40/40/20`을 통계적으로 최적이라고 주장하지 않는다.

사용자는 2026-08-12에 평균·최장·범위를 함께 보는 균형 중심 방향을 승인했다. `balanced-spike-v1`은 다음 검증의 기준 정책이지만 정확한 비율은 아직 변경 가능하다.

### 일행 이동 패턴 정책

- 방장은 `shared_origin`(함께 출발 · 각자 귀가) 또는 `individual_round_trip`(각자 출발 · 각자 귀가)을 선택한다.
- 방장도 추천 대상 참여자 한 명으로 포함하며, 자신의 이동 장소를 제출해야 초대 링크가 활성화된다.
- `shared_origin`에서는 방장이 지정한 공개 출발 장소에서 공원까지의 경로를 재사용하고, 공원에서 각자의 약속 후 장소까지는 별도 계산한다. 참여자 입력이 시작된 뒤 공통 출발 장소는 변경하지 않는다.
- `individual_round_trip`에서는 참여자별 공개 장소 하나를 출발·귀가 기준으로 함께 쓰되 방향별 경로는 별도 계산한다.
- 각 방향은 동일한 `balanced-spike-v1` 평균 40%·최장 40%·범위 20% 부담을 사용한다.
- 최종 이동 부담은 갈 때 50%와 약속 후 50%의 산술 평균이다. 사용자 승인일은 2026-08-12이다.
- 어느 참여자든 한 방향의 경로가 없으면 해당 후보를 제외한다. 성공한 방향만으로 점수를 만들거나 반대 방향 값을 복제하지 않는다.
- 설명은 방향별 원래 시간 지표에서 생성한다. 합산 내부 부담을 객관적 점수처럼 표시하지 않는다.

## 절대 제외 실험안

- 참여자 한 명이라도 경로가 없으면 해당 후보 제외
- 공원이 폐쇄 상태면 제외
- 위험 기상 상태면 제외
- 피크닉 필수 시설인 화장실이 없으면 제외

폐쇄·위험 값은 최신성이 낮아도 안전을 위해 현재 실험에서는 보수적으로 제외한다. 실제 운영에서는 공급자 장애와 오래된 통제를 구분할 추가 정책이 필요하다.

## 상황·신뢰 부담 실험값

| 상태 | 내부 부담 |
|---|---:|
| 보통 혼잡 | 4 |
| 혼잡 / 매우 혼잡 | 12 / 24 |
| 주의 날씨 | 12 |
| 중간 / 큰 행사 영향 | 8 / 18 |
| 혼잡 누락 / 오래됨 | 15 / 10 |
| 날씨 누락 또는 오래됨 | 12 |
| 행사 누락 또는 오래됨 | 8 |
| 통제 누락 또는 오래됨 | 20 |
| 임시 만남 지점 | 5 |

이 숫자는 단위가 다른 조건을 비교해 보기 위한 초기 테스트 값이다. 실제 약속 사례의 사람 판단과 비교하기 전에는 확정하지 않는다.

12시간 밖 1차 추천에서는 현재 혼잡 그래프를 `오늘 지금 기준` 참고 정보로만 보여주고 추천 배지를 붙이지 않는다. 혼잡 값은 점수에 넣지 않고 `crowd_outside_forecast_window` 근거만 남긴다. 12시간 경계에서 다시 계산하며, 최신 추천에서 오래되거나 없는 값을 ‘한산함’ 또는 ‘좋음’으로 바꾸지 않는다.

### 실제 데이터 선택 — 구현 중 정책

- 사용자가 카카오 키워드 검색 결과에서 선택한 공개 장소 ID와 이름을 서버에서 재검증한다. 검색 좌표는 브라우저나 약속에 저장하지 않고 경로 계산 시 서버 메모리에서만 사용한다.
- 선택한 출발 장소와 공원별 만남 지점을 좌표화한 뒤, 모든 참여자의 대중교통 경로가 있는 후보만 평가한다.
- 카카오가 반환한 경로 중 `totalTime`이 가장 짧은 경로를 분 단위로 반올림해 이동시간으로 사용한다. 이 값은 조회 시점 기준이며 약속 시각 시간표를 반영한 값으로 표현하지 않는다.
- 동일 출발 장소-만남 지점 성공 경로는 서버 메모리에서 2시간, 실패는 30초 캐시한다. 프로세스별 하루 900회 방어선 이후에는 추가 조회를 중단한다.
- 일부 경로 누락을 평균이나 fixture로 보완하지 않는다. 유효 후보가 세 곳 미만이면 추천을 중단하고 재시도 안내를 표시한다.

- 서울시 공원별 응답은 서버 메모리에서 5분간 캐시한다. 같은 공원의 동시 요청은 하나로 합친다.
- 약속 시각과 차이가 30분 이내인 공식 예측 중 가장 가까운 항목을 사용한다. 정확히 같은 차이면 더 늦은 예측을 선택해 혼잡을 과소평가할 가능성을 줄인다.
- 공식 예측이 30분 안에 없고 약속 시각이 API 조회 시각에서 30분 이내라면 현재 관측 혼잡을 사용한다.
- 두 조건을 모두 만족하지 않으면 `outside_forecast_window` 또는 `forecast_unavailable`로 표시하고 혼잡 단계를 추정하지 않는다.
- 관측 시각이 조회보다 45분 넘게 오래되면 현재와 그 응답에서 파생된 예측을 `stale`로 감점한다. 45분은 2026-08-12 표본의 약 30~32분 지연을 허용하기 위한 초기 운영값이며 반복 관측 전에는 확정 정책이 아니다.
- 카카오와 서울시 소스가 모두 성공하면 화면은 `LIVE ROUTE · LIVE CROWD`로 표시한다. 키가 없거나 한 소스만 연결된 개발 환경은 데이터 상태를 별도로 구분한다.

## 동률과 표현

- 총 부담 차이가 3 이하이면 `nearTie`로 표시해 근소한 차이를 압도적 우위처럼 표현하지 않는다.
- 정확히 같으면 최장 이동시간, 평균 이동시간, 안정적인 공원 ID 순서로 결정한다.
- 사용자 설명에는 임의의 총점을 내세우지 않는다. 예: “반포보다 평균 6분 더 걸리지만, 반포의 매우 혼잡한 예측과 큰 행사 영향을 피합니다.”
- 출발지 원문이나 참여자 별칭은 설명에 넣지 않는다.

## 아직 확정하지 않은 것

- 균형 중심 안의 최종 가중치
- 절대 이동시간 상한 또는 참여자 간 허용 차이
- 비·강풍을 주의/위험으로 바꾸는 기상 임계값
- 행사 영향 정규화 기준
- 최신성 임계값과 누락 데이터의 정확한 부담
- 실제 사용자 화면의 신뢰도 표현
- 대표 경험 태그를 1순위 적합도 점수에 포함할지 여부
